Most free AI code review options assume the code lives on GitHub. On GitLab Self-Managed, Azure DevOps Server or Bitbucket Data Center, the realistic choices are an open-source reviewer you host yourself and pay only for the model calls, or a hosted tool's trial. The free-for-open-source programs that dominate "free code review tools" lists are gated on GitHub and on the repository being public there, which describes very few of the teams still running a self-managed forge.

## What free means for a self-managed forge

Self-hosted open source is the dependable category. You run the tool, it reads a git diff, and the only external dependency is a model endpoint you already control. That works behind a firewall because nothing outside has to reach into your forge.

A hosted tool's free tier sits at the other end, and its shape moves. CodeRabbit's [current pricing page](https://www.coderabbit.ai/pricing) lists Essentials at $24 per developer per month billed annually, Team at $48, Advanced at $72, and a custom Enterprise tier, with a 14-day trial on all of them. No free plan appears on that page, and self-hosting is listed as an Enterprise feature. A recommendation that starts with "it's free" ends, for a GitLab Self-Managed team, on a trial and then on a sales call.

Forge-native features are the last corner. GitLab's [Code Review Flow page](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/) lists the tier as Free, Premium and Ultimate across GitLab.com, Self-Managed and Dedicated, and notes it can run with self-hosted models; what that costs depends on the Duo entitlement your instance carries, and the [edition split for AI review on self-managed GitLab](https://mergerequests.dev/blog/gitlab-self-managed-ai-review-that-follows-your-own-rules/) is where the decision actually lands. Azure Repos has no comparable native reviewer on Server, because Copilot code review is documented for Services. Bitbucket's native AI review is Cloud-only, which the [Bitbucket Data Center breakdown](https://mergerequests.dev/blog/ai-code-review-on-bitbucket-data-center-whats-native-what-isnt/) covers end to end.

## Self-hosted routes that cover all three forges

Three options are worth putting on the shortlist for a self-managed GitLab, an Azure DevOps Server behind a firewall, or a Bitbucket Data Center: PR-Agent, Alibaba's Open Code Review, and Kodus Community. They differ in how they attach to the forge, which matters more than the feature list when the forge is internal.

### PR-Agent after the Qodo donation

[PR-Agent](https://github.com/The-PR-Agent/pr-agent) is a community-owned project that Qodo donated, and the repo now sits in the PR-Agent org under an MIT license. It is explicitly not Qodo's product for open-source projects, which lives elsewhere, and the README notes the project is in the process of being donated to an open-source foundation.

The supported-platform matrix on [the current PR-Agent docs](https://docs.pr-agent.ai/overview/supported_platforms/) lists Describe, Review, Improve, Ask, Add Docs and Help as supported on GitHub, GitLab, Bitbucket, Azure DevOps and Gitea, with CLI and app/webhook deployment available on all five. Gerrit and CodeCommit are registered providers kept out of that main table, and they do not support GitHub-flavored markdown, so `/describe` drops the semantic file-type sections there.

A few rows in that matrix are provider-specific, and they are the ones that decide whether the tool feels native on your forge. The tagging bot is GitHub-only. Several tools run but post their output as a comment instead of applying it where the provider cannot write files. `/help_docs` has been disabled since v0.36.1 while a credential-exposure issue is fixed.

Where a deployment lives is worth reading before you upgrade anything, because the Docker namespace moved. Releases from 0.34.2 are published under `pragent/pr-agent`; anything up to and including v0.31 stays at the frozen `codiumai/pr-agent` namespace with no new pushes. If a pipeline pins an old image reference, that is the first thing to fix.

The newer part of PR-Agent is the instructions layer. [Agent Skills](https://docs.pr-agent.ai/core-abilities/agent_skills/) let you keep a curated set of `SKILL.md` files on the host and have their name, description and body injected into `/review`, `/improve`, `/describe` and `/ask`. Two constraints are worth knowing before you plan around it. Skills are disabled by default, and `skills.paths` can only be set at host level, never from a repository's own `.pr_agent.toml`, because a repo that could redirect the filesystem scan could point the tool at files like `~/.ssh/*` and pull them into a model prompt. A repo can only opt in or size the token budget. The other constraint is architectural: PR-Agent makes single-shot model calls, so the standard's progressive-disclosure model does not apply, and every enabled skill's text goes into every pull request prompt up to the token cap. Files in `scripts/` and `assets/` are skipped, so a skill that depends on running a script will not work.

Deployment detail per forge is where the interesting bits are, and I have separate notes on [running PR-Agent on self-managed GitLab](https://mergerequests.dev/blog/pr-agent-on-self-managed-gitlab-pipeline-or-webhook/) and on [PR-Agent on Azure DevOps](https://mergerequests.dev/blog/pr-agent-on-azure-devops-pipelines-branch-policies-webhooks/), since Azure Repos needs Branch Policies rather than a YAML trigger.

### Open Code Review

[Open Code Review](https://github.com/alibaba/open-code-review) is Alibaba's internal review assistant, released as an Apache-2.0 CLI. Because it operates on a git diff instead of on a forge API, it does not care where the repository is hosted, and it needs Git 2.41 or newer. Install is `npm install -g @alibaba-group/open-code-review`, then `ocr config provider` and `ocr config model`.

The command set is broader than a single review pass. `ocr review` covers staged, unstaged and untracked changes in the workspace, `ocr review --from main --to feature-branch` covers a branch range, `ocr scan` reviews whole files with no git history, and `ocr delegate` lets a host coding agent perform the review itself, in which case no separate model key is needed.

The project's headline claim is a precision argument, and the numbers are its own. Its benchmark is built from 50 popular repositories, 200 real pull requests, 10 languages and 1,505 annotated issues cross-validated by more than 80 senior engineers, and the README states that it beats a general-purpose agent on the same underlying model on precision and F1 while using roughly a ninth of the tokens. Recall is deliberately lower. Treat that as a design claim from the project rather than an independent result, and note that the trade-off it describes is real for review tooling: fewer comments that are more often correct reads better in a busy pull request than broad coverage with a long tail of noise.

### Kodus Community

[Kodus](https://docs.kodus.io/en/how_to_use/pricing.md) publishes a free Community tier that runs self-hosted or on their cloud, with reviews unlimited on every plan because the model calls run on your own provider key. That combination is what makes it relevant here: free, self-hostable, and not gated on the repository being public on GitHub.

Two limits shape whether it fits. Community allows up to 10 Kody Rules and 3 plugins, and a self-hosted instance running without a valid license evaluates at most 10 rules per review, oldest first, so an instance with a larger rule library will silently stop firing rules past that point. The [rules file detection](https://docs.kodus.io/en/how_to_use/code_review/configs/rules_file_detection.md) list is long for a tool at this stage: `AGENTS.md` and its dotfile variants, `.cursorrules` and `.cursor/rules/**/*.mdc`, `.github/copilot-instructions.md` and `.github/instructions/**/*.instructions.md`, `CLAUDE.md`, `.windsurfrules`, `.aider.conf.yml`, `.sourcegraph/**/*.rule.md`, plus a generic `docs/coding-standards/**` pattern. Matching is case-insensitive, nested files are discovered and scoped to their directory, and `@file` references inside a rule file are followed one level deep. Files that match the repository-rules template are imported verbatim without an LLM rewriting them, which is the difference between your standards surviving import and being paraphrased.

Connecting it to a self-managed forge is where the free tier gets plainer. The quickstart documents OAuth (recommended) or token for GitHub and GitLab, and token only for Bitbucket and Azure DevOps, with no OAuth path for either. Internal GitLab, Bitbucket Data Center and Azure DevOps Server instances connect by allowlisting a fixed IP. On the licensing point, the repository is public and tagged open source, but GitHub's API reports the license as "Other" rather than an OSI identifier, so if an approved license matters to procurement, read the license file rather than the tag.

## The hosted free tiers, measured against self-managed editions

CodeRabbit and Qodo are the two hosted tools most often recommended to teams asking this question, and neither free path is shaped for a self-managed forge. CodeRabbit's pricing page carries no free plan, only the 14-day trial, and separately lists per-developer hourly review limits that rise by tier, with usage-based reviews at $0.25 per reviewed file past the included allowance. Qodo's free offering for open-source projects is described on the PR-Agent README as a distinct product from the open-source agent, and it is aimed at public projects.

For the on-prem side of both vendors, what they document differs by forge and edition, and the [per-docs comparison of CodeRabbit and Qodo for self-hosted deployments](https://mergerequests.dev/blog/self-hosted-ai-code-review-coderabbit-and-qodo-per-their-docs/) is where that belongs. The short version for this page is that self-managed coverage is an enterprise arrangement in both cases, which is exactly why the free routes above exist.

## Picking one for a self-managed forge

If the constraint is that no third party reaches into the forge, the decision is between two shapes of tool rather than three products. PR-Agent and Open Code Review both run as a CLI or webhook with a model endpoint you already have, and the difference is in the review model. PR-Agent reviews through the forge, which is why it has per-provider docs, comment commands and, on some providers, tools that can only post a comment rather than apply a change. Open Code Review reviews a diff, which is why it works anywhere and why it has no comment commands or PR descriptions at all. Choose PR-Agent if you want the reviewer to behave like a native bot in merge requests, and Open Code Review if you want a precision-biased pass over changes and whole files from a pipeline.

Kodus Community is the option to look at when the reason you want a reviewer is your own written standards. Its rule import covers more of the instruction-file formats teams have already checked into repositories than the alternatives here, and per-directory scoping is built into detection, which matters in a monorepo. The trade-off is the ceiling on Community: 10 Kody Rules and 3 plugins, with the unlicensed self-hosted rule cap on top, so a team with a large standards library is choosing between paying for a licence and pruning rules.

Whatever you pick, check the vendor or project page for your edition before you commit to it, because edition support and free-tier scope drift faster than the rest of the documentation. The Docker namespace change in PR-Agent and the absence of a free plan in CodeRabbit's current lineup are both recent examples of the same thing: a "free" answer that was true last year and is not true in your upgrade path.
