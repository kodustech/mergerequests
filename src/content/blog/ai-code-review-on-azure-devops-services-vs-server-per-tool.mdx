Azure Repos ships in two editions, and the AI review options do not line up between them. Copilot code review runs on Azure DevOps Services, where Microsoft now ships it in public preview, and there is no Microsoft-native equivalent on Azure DevOps Server. A server team runs PR-Agent from a pipeline, wires a vendor integration into Service Hooks, or self-hosts a product. The edition decides the setup work, the permissions, and how a reviewer learns your coding standards.

## Copilot code review is Azure DevOps Services only, and it is in public preview

The [get started page](https://learn.microsoft.com/en-us/azure/devops/repos/git/copilot-code-reviews?view=azure-devops&tabs=preview) is headed Azure DevOps Services and states that the feature is in public preview, so the terms are the usual preview ones: no SLA, and functionality can change or be removed. The prerequisites are an Azure DevOps organization, a Git repository in Azure Repos (TFVC is not supported), and an Azure subscription linked to the organization, because usage is billed through Azure Cost Management rather than through seats.

Enablement cascades across three scopes. A Project Collection Administrator turns the feature on at the organization level and can enable every project at once. A Project Administrator can scope it to specific projects, and a repository owner enables it per repository when project settings allow that. Individual users opt in through Preview features unless an administrator has enabled the preview for everyone in the organization.

Effort level is the setting that decides how much work each review gets. A project administrator sets the default for all repositories and decides whether repository administrators may override it, and a reviewer can pick a different level for a single review without changing either default. Higher effort consumes more tokens. The naming is unsettled: the product page screenshots show an inherited Medium default, while the [September devblog update](https://devblogs.microsoft.com/devops/updates-to-copilot-code-reviews-for-azure-repos/) describes setting the default to Lite or Balanced at the project and repository level. Read the labels on your own settings page rather than planning around the blog post.

The compute dependency is the constraint to check first. Copilot code review uses Azure Pipelines to orchestrate reviews. Reviews run on Microsoft-hosted agents by default, and organizations on Managed DevOps Pools can select a pool at the organization level, after which every Copilot review in that organization runs on it. Self-hosted agents are not supported, per the [public preview announcement](https://devblogs.microsoft.com/devops/copilot-code-reviews-for-azure-repos-public-preview/). An organization that runs everything on self-hosted agents has no supported path here, and that is not something you can configure around. The [compute dependency compared across the three forges](https://mergerequests.dev/blog/ai-review-compute-gitlab-runners-azure-agents-bitbucket-dc-builds/) is worth reading next to this section, because GitLab and Bitbucket DC put the runner decision in your hands and this feature does not.

Automatic reviews are a separate setting from enablement. To have Copilot review without anyone requesting it, an administrator configures a branch policy on each target branch where reviews should run, which requires permission to edit policies for that branch. Without the policy, someone adds Copilot as a reviewer by hand. Automatic reviews do run on draft pull requests, which matters if you use draft state to keep work off the merge queue: [draft mode changes other rules on Azure Repos](https://mergerequests.dev/blog/draft-prs-on-gitlab-azure-repos-and-bitbucket-dc-what-ai-review-skips/) while this one still fires.

### The gates and limits that decide whether a review happens

The same page publishes hard gates and concurrency limits, and they decide whether a review is produced at all.

| Gate | Value |
| --- | --- |
| Pull request status | Active |
| Pull request merge status | No merge conflicts (Merge Succeeded) |
| Repository size | 10 GB or less |
| Changed files in the pull request | 100 files or fewer |
| Number of changes in the pull request | 100 changes or fewer |

| Limit | Value |
| --- | --- |
| Duplicate review on the same pull request version | 1 completed review per merge commit |
| Concurrent reviews per pull request | 1 |
| Concurrent reviews per organization | 5 |
| Concurrent reviews per user | 2 |

The 100-file ceiling sits well below what the forge itself is willing to render, so a large generated change can be reviewable in the UI and unreviewable by Copilot. The concurrency of five per organization is the number to watch if you enable the feature widely: reviews queue rather than fail, and a queued review looks like a slow review.

Re-reviews are manual. Copilot does not review a pull request again when new commits land, so after a push someone selects Request again next to GitHub Copilot in the Reviewers list. Copilot always leaves a Comment review and never approves or requests changes, so its review does not satisfy a required-reviewer policy and does not block a merge. If you want a gate, the gate has to be a branch policy or a status check you set up separately, which is the shape described in [Azure Repos merge gating for AI reviewers](https://mergerequests.dev/blog/azure-repos-merge-gating-for-ai-reviewers-the-status-check-policy/).

Two operational changes landed over the last few months and are worth wiring up before a wide rollout. Copilot Code Review usage now carries Azure DevOps project tags in Azure Cost Management, so spend can be grouped by project instead of only at the organization level, and budget alerts can be scoped to that meter. The September update also added audit log events for enablement changes at each scope, agent pool changes, custom instruction changes, effort level changes, and branch policies added for automatic reviews. On a feature billed per review, those events are how you find out who turned it on.

## How Copilot reads your team's rules, and the target-branch rule

Copilot code review takes instructions at the organization and project level through Azure DevOps settings, and at the repository level through a file. The [instructions page](https://learn.microsoft.com/en-us/azure/devops/repos/git/configure-copilot-code-review-instructions?view=azure-devops) accepts two paths for that file: `.github/copilot-instructions.md` or `.azuredevops/copilot-instructions.md`, both at the repository root. The second path matters if your team already keeps Copilot instructions under `.github/`.

Path-scoped files go in `.github/instructions/` or `.azuredevops/instructions/` as `*.instructions.md`, with YAML front matter carrying an `applyTo` value. A path-scoped file without `applyTo` is skipped, and nothing reports an error when that happens. The file is committed, no review uses it, and the only signal is a rule you expected to see that never appears.

When instructions exist at more than one scope, Copilot applies all applicable ones and resolves conflicts by precedence: repository first, then project, then organization. The page adds that the order guides review behavior and is not guaranteed, because a language model can interpret conflicting instructions differently. Read that as a tie-breaker for instructions that overlap, and as no help at all for instructions that contradict each other.

Which branch the files come from changes rollout. Repository-level and path-scoped files are read from the pull request's target branch. A pull request that adds or edits the instructions file is not reviewed against the new text, and those rules apply once the change is merged into the target branch. Land the instructions file on the default branch first, then open the pull requests that should be reviewed against it.

For a team on Azure DevOps Server, none of that applies.

## What runs on Azure DevOps Server instead

On the server edition the choice is between self-hosted tools and hosted vendors that reach into your instance.

[PR-Agent](https://docs.pr-agent.ai/overview/supported_platforms/) lists Azure DevOps as a supported provider, and the support matrix marks an Azure DevOps pipeline as supported usage, so a Server team can run it as a pipeline job or behind a webhook. It is MIT licensed and community-owned. Review categories and prompts live in configuration files you own, and the matrix lists repo context files such as `AGENTS.md` and agent skills among the core abilities that work on every provider. That combination is what makes it the default starting point for a Server team that wants review output posted on the pull request, and the [pipeline and Branch Policies notes](https://mergerequests.dev/blog/pr-agent-on-azure-devops-pipelines-branch-policies-webhooks/) cover the wiring.

[Open Code Review](https://github.com/alibaba/open-code-review) from Alibaba is a different shape. It installs from npm as `ocr`, works on a git diff, a commit range, or a whole-file scan, and needs an LLM endpoint rather than a forge integration. On a firewalled Server install that is convenient, and it also means the tool does not post comments to a pull request unless you wire that up. Its published benchmark is the project's own, built from 50 repositories and 200 pull requests with engineer-annotated issues, and it reports higher precision than a general-purpose agent on the same model at roughly a ninth of the tokens, with lower recall as a stated trade-off.

Hosted vendors document this edition less clearly. [CodeRabbit's Azure DevOps page](https://docs.coderabbit.ai/platforms/azure-devops) covers a PAT or a Microsoft Entra service principal, Project Administrator or Project Collection Administrator rights, and the Edit Subscriptions permission on Service Hooks so the webhook can be installed, and notes that permission is granted per project and cannot currently be granted through the UI. The page does not split Azure DevOps Services from Azure DevOps Server, so it does not establish Server support on its own.

[Qodo's on-premises Azure DevOps guide](https://docs.qodo.ai/on-prem/git-integration/install/azure-devops) has the same gap from the other direction. It walks through a Microsoft Entra app registration, a service account added to the Azure DevOps organization with Basic access and Project Administrators, and a Service Hooks webhook subscribed to PR Created, PR Updated, PR Commented and PR Merged. Those steps assume `dev.azure.com` and Entra ID, which are Azure DevOps Services constructs, while the [deployment matrix](https://docs.qodo.ai/install-qodo/deployment-model-support) marks on-prem as unsupported for Azure DevOps Cloud. Read together, the guide covers running Qodo on-premises against Azure DevOps Services, and the two pages answer different questions.

Kodus connects to Azure DevOps with a token, and its [quickstart](https://docs.kodus.io/en/how_to_use/quickstart) documents no OAuth path for that provider, unlike GitHub and GitLab. The same page covers the Server case directly: a self-hosted Azure DevOps Server instance needs Kodus's IP `52.55.217.197` allowlisted before the connection works. Rules come from Kody Rules in the product plus the coding-agent files Kodus detects, and the [rule file detection page](https://docs.kodus.io/en/how_to_use/code_review/configs/rules_file_detection) lists `.github/copilot-instructions.md` and `.github/instructions/**/*.instructions.md` among the supported patterns, not the `.azuredevops/` paths. On the free Community edition, which can run self-hosted, the [pricing page](https://docs.kodus.io/en/how_to_use/pricing) caps Kody Rules at 10 and plugins at 3, with reviews unlimited on your own model key.

## Which routes follow your rules, by edition

| Route | Azure DevOps Services | Azure DevOps Server | Where rules come from | Where the review runs |
| --- | --- | --- | --- | --- |
| Copilot code review | Yes, public preview | Not documented | Org and project settings, `.github/` or `.azuredevops/` instruction files, precedence repository then project then organization | Azure Pipelines, Microsoft-hosted agents or a Managed DevOps Pool |
| CodeRabbit | Documented (Entra service principal or PAT) | Not stated | Web UI and repository configuration files | CodeRabbit cloud, via Service Hooks |
| Qodo on-premises | Documented through Entra ID and Service Hooks | Not documented | Repository configuration and PR commands | Your Qodo on-premises environment |
| PR-Agent | Supported provider, pipeline or webhook | Supported provider, pipeline or webhook | JSON config, prompt files, `AGENTS.md` | Your pipeline, CLI, or webhook server |
| Open Code Review | CLI on a git checkout | CLI on a git checkout | Path-scoped review rules | Wherever you run the CLI |
| Kodus | Documented, token auth | Documented via IP allowlist | Kody Rules plus detected repository rule files | Kodus self-hosted or cloud |

Every row reflects the vendor or project page linked above. Where a cell says not documented or not stated, the page I read does not cover that edition, and that gap is the thing to verify before a rollout.

## Deciding

On Azure DevOps Services, Copilot code review is the shortest path to a first automated review. It is in public preview, the enablement chain is three toggles, billing runs through a subscription you already have, and reviewers appear on pull requests without a webhook to maintain. The constraints that decide whether it fits are the agent pool (Managed DevOps Pools yes, self-hosted agents no), the 100-file and 100-change ceilings, and the target-branch rule for instruction files. If your standard is that a reviewer applies a rules file changed inside the same pull request, Copilot will not do that, and you want a tool that reads the rule at review time.

On Azure DevOps Server the choice is between PR-Agent and a self-hosted product. PR-Agent is the lower-commitment option: MIT, no vendor account, configuration stored in files in your repository, and a documented pipeline trigger. What you pay for it is operational work, since you own the pipeline, the model key, and the webhook endpoint. Generated rules, a UI for managing them, and review metrics are where a product starts to make sense, and the price of that is either the Community limits above or a commercial plan. The [self-managed comparison](https://mergerequests.dev/blog/ai-code-review-tools-on-self-managed-gitlab-azure-repos-and-bitbucket/) covers the same question across all three forges.

The cheapest test before committing to any of them is one pull request. Put a single rule in the file that route reads, open a pull request that breaks the rule, and see which reviewers flag it. On Azure Repos the file that reaches the most reviewers is `.github/copilot-instructions.md`, since Copilot reads it and Kodus detects it among its supported patterns. If your repository already speaks `.azuredevops/`, keep both paths in sync or the tools will read different standards.
